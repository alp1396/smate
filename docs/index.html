SMate

From developers to developers :)

An isolated sandbox for development tasks. A person, or their agent, works inside a Docker container, and the only thing that leaves it is a validated patch series — no access to the working .git, its history, remotes or your keys.

Requirements: Go 1.24+ · git · a running Docker

smate

Bare smate — every task, its status, its run, and whether a result was actually written.

The loop

One shape, every time

What goes in is a flat snapshot of tracked files. What comes back is a patch series, checked on the host before anything lands.

Hostgit archive HEAD
→
Sandbox/workspace in smate-<id>
→
Sandboxwork · commit locally
→
Hostformat-patch · validate
→
Hostgit am → branch <id>

The way in

A git archive of an exact commit — tracked files and nothing else. Paths listed under secrets are cut before the container starts, so they never reach it at all. Inside lives a throwaway git with a single baseline commit: no remote, no credentials, no history to mine.

The way out

A patch series diffed against that baseline, and nothing else — there is no third channel. It is parsed on the host as untrusted input and applied to a branch named after the task, starting at the commit the snapshot was taken from.

▣

The AI lives in Docker only

Every agent CLI runs inside a disposable container and nowhere else. It never runs as a process on your machine, and the container is thrown away when the task is done.

⇄

Strictly deterministic exchange

Two openings, both fixed: a snapshot in, a patch series out. Not a protocol the agent can negotiate — the host decides what enters and validates everything that leaves.

⌾

No reach into your host data

No working .git, no history, no remotes, no SSH or cloud credentials, no files outside the snapshot — only what you mounted on purpose.

!

The honest part

Docker isolation cannot stop an AI from trying to break out of it — least of all if you explicitly ask it to. The container has full capabilities, a writable root filesystem and open outbound network; a determined escape is a matter of the kernel and the runtime, not of this tool.

Full isolation of your data is something you get by working on a remote machine, where there is nothing of yours to reach in the first place. Such is the cruel truth of the current state of affairs :)

The interface

Five views of the same work

A single terminal UI over the whole loop — no dashboard, no daemon, no browser.

smate

The tasks list, monitored in realtime

Every task with its status, the branch it came from, the role running right now and the artefact it has produced — so the whole AI workflow is one screen, computed fresh on every open rather than from a daemon's memory.

smate — task bug-193

Everything a task can do, on one screen

Apply the work, drop into a shell, open a harness by hand, start a role, clean up — with apply, clean and stop asking first, since they are the three that cannot be taken back.

smate — role coder

A role is a described performer

Which harness runs it, with what command, which artefacts it needs and which one it must leave behind — so a run refuses to start on a missing input instead of inventing one.

smate — logs

The run outlives your terminal

It lives in a tmux session inside the container: watch its screen as it prints, then attach to answer a question and detach again without killing it.

smate — artefacts

Roles hand work to each other in files

The request, the note for the run, the reports left behind — all in .smate/, which never reaches a commit. The diff tab shows what the sandbox actually changed, before any of it goes near your repository.

Quick start

Install once, run from your repo

Two commands to set up, four to go around the loop.

# install, then build an environment image
$ make install
$ smate build base
$ smate build php

Images live in ~/.smate/images/<name>/Dockerfile and are yours to edit — base, php, node and go ship with the binary.

# a typical round, by hand
$ smate start 123   # snapshot → container
$ smate shell       # work inside it
$ smate apply       # → branch 123
$ smate clean       # drop it all
or
$ smate

Just run smate — the same round, and every role with it, is a few keypresses away in the control panel — including run, attach and logs for an agent.

The boundary

What is checked before an import

Isolation is the container and the shape of the exchange, not the agent's good behaviour. Everything coming out is untrusted input — the whole series is refused if it:

  • escapes the repository root
  • touches anything inside .git/ or .smate/
  • contains a symlink
  • covers a path listed under secrets
  • carries the literal value of one of your configured keys
  • lands on a working copy that is not clean, or a branch smate did not create
  • an added +x bit is reported as a warning, not a refusal

A refused import puts you back where you were and marks the task REJECTED — go into shell, fix it, apply again. Nothing is lost: every commit smate imported can be produced from the sandbox a second time. The limitations are written down just as plainly — the key scan catches the accident, not the intent.
